# AI Helper 整体架构设计

## 1. 设计目标

`AI Helper` 面向的是一个具备会话记忆、知识增强、工具调用与复杂任务执行能力的智能助手系统。  
整体架构设计需要同时满足以下目标：

- 支持多轮对话与多会话管理
- 支持领域知识增强与长期可扩展的 RAG 体系
- 支持工具调用、联网查询与本地任务执行
- 支持复杂任务的多步规划与执行反馈
- 支持前后端分离与流式交互体验
- 支持后续按模块独立演进，而不是把全部能力耦合在单体工程中

因此，系统从一开始就不按“单服务 + 单模型接口”的方式设计，而是按“网关 + 主智能体服务 + 通用工具服务 + 前端工作台 + 多存储支撑”的方向规划。

---

## 2. 总体架构思路

### 2.1 总体设计原则

本项目整体架构遵循以下原则：

- 领域能力与通用能力分离
- 模型调用与业务控制分离
- 短期上下文与长期记忆分层
- 检索增强链路独立设计
- 工具能力采用可插拔方式接入
- 前端围绕“智能体工作台”而不是“普通聊天框”设计

### 2.2 总体架构图

```text
用户 / 浏览器
    |
    v
front-show（Vue3 工作台）
    |
    v
ai-gateway（统一入口）
    |
    +-------------------------> ai-kitchen-brain-service（领域主脑）
    |                               |
    |                               +--> 会话管理
    |                               +--> 对话编排
    |                               +--> 会话记忆
    |                               +--> RAG 检索增强
    |                               +--> ReAct 多步规划
    |                               +--> Tool / MCP 调用
    |                               +--> 文档生成
    |
    +-------------------------> ai-utility-agent-service（通用工具智能体）
                                    |
                                    +--> 通用问答
                                    +--> 通用 MCP / 工具能力


ai-kitchen-brain-service / ai-utility-agent-service
    |
    +--> MySQL（业务数据、会话历史）
    +--> Redis（短期记忆、缓存）
    +--> RocketMQ（异步摘要与任务解耦）
    +--> PostgreSQL + pgvector（RAG 知识库）
    +--> 本地文件系统（文档输出）
```

这个架构的核心思想是：

- `ai-kitchen-brain-service` 作为主智能体服务，承载主要业务闭环
- `ai-utility-agent-service` 作为通用能力承接层，为非核心领域问题或通用工具类需求提供扩展位
- `ai-gateway` 负责统一入口与路由隔离
- `front-show` 负责把复杂的后端智能体能力以可观测、可交互的形式呈现给用户

## 3. 模块划分设计

## 3.1 ai-common

`ai-common` 作为公共基础模块，负责沉淀跨服务共享能力，主要包括：

- 统一响应结构
- 全局异常处理
- 通用异常码
- 通用工具类
- AOP 日志切面

这样设计的原因是：

- 避免每个服务重复维护基础设施代码
- 保证服务间的接口风格一致
- 便于后续继续扩展公共组件

## 3.2 ai-gateway

`ai-gateway` 作为统一接入层，负责：

- 统一外部访问入口
- 对不同智能体服务做路径级路由隔离
- 屏蔽后端服务地址细节
- 预留后续统一鉴权、限流、日志与监控接入能力

在设计上，网关层不承担业务推理，只承担流量入口和流转职责。

推荐的路由划分如下：

- `/super-host/**` 路由到 `ai-kitchen-brain-service`
- `/code-assistant/**` 路由到 `ai-utility-agent-service`

这样的好处是：

- 主脑服务与通用服务边界清晰
- 前端调用路径稳定
- 后续即使服务独立部署，也不影响前端访问方式

## 3.3 ai-kitchen-brain-service

`ai-kitchen-brain-service` 是系统的核心服务，定位为“领域主脑”。  
它不是简单的聊天接口，而是负责承接整个智能体主流程，包括：

- 会话管理
- 模型调用编排
- 会话记忆装载与持久化
- RAG 检索增强
- ReAct 多步任务执行
- 工具调用与 MCP 扩展
- 文档导出能力

这个模块应当被设计为整个系统的“大脑中枢”。

## 3.4 ai-utility-agent-service

`ai-utility-agent-service` 定位为“通用工具型智能体服务”，主要服务于以下场景：

- 非领域化问题的通用问答
- 通用工具型 MCP 接入
- 独立的工具助手扩展

之所以单独拆一个服务，而不是并入主脑服务，主要基于以下考虑：

- 主脑服务需要聚焦核心领域能力，不应无限堆叠所有通用能力
- 通用工具服务天然更适合快速试验和增删工具
- 两者底层技术栈可以不同，主脑服务偏 Spring AI，工具服务可偏 LangChain4j

## 3.5 front-show

前端工作台不应只被设计为“输入框 + 回复框”，而应承担以下职责：

- 会话列表管理
- 历史消息恢复
- 流式回答展示
- 中间过程可视化
- 工具执行轨迹呈现
- 用户对长任务的等待感知管理

因此前端需要围绕“智能体工作台”来设计，而不是普通客服式聊天页面。

## 4. 核心技术选型设计

## 4.1 后端基础框架

后端基础框架选型如下：

- Java 17
- Spring Boot 3
- Spring Cloud Gateway
- MyBatis
- Redis
- RocketMQ
- PostgreSQL

选型理由：

- Java + Spring Boot 生态成熟，适合快速构建稳定服务
- Spring Cloud Gateway 适合作为统一接入层
- MyBatis 适合当前相对清晰的业务表读写
- Redis 适合短期上下文和高频缓存
- RocketMQ 适合异步任务解耦
- PostgreSQL + pgvector 适合承载知识库检索体系

## 4.2 智能体框架选型

智能体框架不建议只依赖单一方案，而是分模块选型：

- `ai-kitchen-brain-service`：采用 `Spring AI`
- `ai-utility-agent-service`：采用 `LangChain4j`

这样设计的原因：

- Spring AI 更适合与 Spring 体系深度融合，便于主服务中接入 Advisor、RAG、Tool 等能力
- LangChain4j 的接口式 AI Service 和 MCP 集成也比较适合做轻量通用服务
- 双框架并存可以让项目在学习和演进阶段保留灵活性

## 4.3 模型能力选型

模型能力建议按职责拆分，而不是所有场景只用一个模型：

- 对话主模型：用于通用回答与主智能体输出
- Planner 模型：用于 ReAct 规划
- Embedding 模型：用于向量检索
- Rerank 模型：用于检索结果重排
- Summary 模型：用于滚动摘要生成

这种拆分的原因在于：

- 不同任务对模型的要求不同
- 可以分别控制成本、延迟和效果
- 后续可以灵活切换模型实现而不改整体架构

## 5. 主智能体服务内部设计

## 5.1 分层结构

`ai-kitchen-brain-service` 内部建议拆为以下几层：

- Controller 接口层
- Service 编排层
- Advisor 增强层
- Agent / ReAct 层
- RAG 层
- Tool / MCP 层
- Persistence 数据访问层

它们的职责分工如下：

### 接口层

负责暴露以下能力：

- 会话创建、查询、重命名、删除
- 历史消息查询
- 非流式对话
- 流式对话

### 编排层

编排层负责决定：

- 是走普通直答链路还是 ReAct 链路
- 是否挂载记忆能力
- 是否挂载 RAG 增强能力
- 是否对外以流式方式返回

### Advisor 层

Advisor 层的设计目的，是把“记忆加载、检索增强、结果持久化”从业务代码中抽离出来，形成统一模型调用增强链。

### ReAct 层

负责复杂任务的多步规划、工具执行和 observation 回灌。

### RAG 层

负责查询改写、召回、融合、重排和上下文注入。

### Tool / MCP 层

负责统一接入本地工具和远程 MCP 工具。

## 6. 会话与记忆设计

## 6.1 设计目标

会话记忆体系需要解决两个核心矛盾：

- 长对话必须可恢复
- 模型上下文不能无限膨胀

因此，本项目不应把所有历史对话直接塞给模型，而应该采用“短期窗口 + 长期摘要 + 全量历史持久化”的三层设计。

## 6.2 存储结构设计

建议设计三张核心业务表：

- `session`
  - 存储会话元信息

- `chat_history`
  - 存储完整消息流水
  - 同一轮对话通过 `turn_no` 关联用户和助手消息

- `chat_summary`
  - 存储滚动摘要
  - 维护摘要推进游标

同时在 Redis 中设计两类缓存：

- `summary:{sessionId}`
  - 长期摘要缓存

- `window:{sessionId}`
  - 最近 N 轮对话窗口

## 6.3 记忆加载设计

在模型调用前，需要通过统一的记忆加载组件完成以下动作：

1. 根据会话 ID 读取摘要
2. 根据会话 ID 读取最近窗口对话
3. Redis 命中优先，数据库回源兜底
4. 将摘要作为高层上下文注入
5. 将最近窗口对话作为近场上下文注入

这样做的原因是：

- 摘要负责保留长期偏好、背景和历史结论
- 窗口负责保留最近轮次的细节
- 两者配合可以较好地平衡效果和上下文长度

## 6.4 记忆持久化设计

在模型完成回答后，需要统一进行记忆落盘：

1. 写入用户消息
2. 写入助手消息
3. 推进会话最新历史指针
4. 更新 Redis 窗口缓存
5. 判断是否需要推进滚动摘要

## 6.5 摘要异步化设计

滚动摘要不建议放在主链路同步执行，而应采用异步消息化方案：

- 当窗口即将淘汰旧轮次时，发送摘要生成事件
- 由 MQ 消费者异步处理摘要生成
- 基于“旧摘要 + 新增淘汰轮次”生成新摘要
- 再回写 MySQL 和 Redis

这样设计的好处是：

- 不阻塞主对话请求
- 可以把长会话压缩为稳定大小的摘要
- 为未来更复杂的记忆治理预留扩展空间

## 7. RAG 架构设计

## 7.1 设计目标

RAG 设计目标不是简单接一个向量库，而是构建完整的检索增强链路，提升复杂问答、知识查询和专业领域推理的稳定性。

RAG 体系建议包含以下环节：

- 查询改写
- 多路召回
- 结果融合
- 模型重排
- 上下文注入

## 7.2 知识库存储设计

知识库不建议与业务 MySQL 混用，应独立放在 PostgreSQL 中，原因如下：

- 更适合承载全文检索
- 更适合扩展 pgvector
- 更适合构建独立知识库表结构

建议的知识库表设计包括：

- `kb_doc`
  - 文档主表
  - 管理文档级元数据

- `kb_chunk`
  - 分块表
  - 保存文本块、全文检索字段和向量字段

- `kb_ingest_task`
  - 入库任务表
  - 管理知识导入过程与结果

## 7.3 查询改写设计

多轮对话下，用户问题经常存在代词、省略、上下文承接等问题。  
因此在正式检索前，需要增加 Query Transformer，用于：

- 补全用户真实检索意图
- 结合最近上下文进行问题重写
- 提高召回命中率

## 7.4 多路召回设计

为了避免单一路径召回不稳定，建议采用双路召回：

- 关键词召回
- 向量语义召回

其中：

- 关键词召回保证字面精确命中
- 向量召回保证语义相关命中

双路并行召回之后再做统一融合。

## 7.5 融合与重排设计

召回后的候选文档建议经历两步筛选：

1. 使用 RRF 等策略做多路融合
2. 使用 rerank 模型做语义重排

这样的设计优于“直接按相似度取前 K 条”，因为：

- 可降低单路偏差
- 可提升最终候选文档排序质量
- 更适合复杂知识问答场景

## 8. ReAct 智能体架构设计

## 8.1 设计目标

当用户请求不是简单问答，而是需要多步行动、工具调用或结果整合时，应引入 ReAct 架构。

ReAct 设计目标如下：

- 支持模型分步规划
- 支持工具调用
- 支持工具结果回灌
- 支持失败后修正参数或重新规划
- 支持最终答案输出

## 8.2 角色拆分

建议将 ReAct 子系统拆成两个核心角色：

- Planner
  - 只负责决定下一步做什么

- Agent Executor
  - 负责真正执行工具、保存 observation、驱动下一轮规划

这样设计的原因是：

- 规划与执行职责清晰
- 更方便后续单独替换 Planner 模型
- 更容易做可观测性与容错

## 8.3 执行流程设计

完整流程如下：

1. 获取用户输入
2. 收集可用工具列表
3. Planner 输出结构化动作
4. 若动作为 `ANSWER`，直接生成结果
5. 若动作为 `TOOL_CALL`，执行目标工具
6. 将 observation 记录到步骤上下文
7. 再次交给 Planner 继续推演
8. 达到完成条件后输出最终答案

## 8.4 容错设计

ReAct 链路必须具备容错机制：

- 限制最大步数
- 连续失败达到阈值时停止循环
- 无法收敛时自动降级为普通回答

这是避免多步智能体进入死循环或完全不可用的关键设计。

## 8.5 可观测性设计

ReAct 的中间过程不应只留在服务端日志中，而应通过流式事件向前端透出，包括：

- 开始执行
- 规划完成
- 工具开始
- 工具结束
- 步骤失败
- 降级执行
- 最终回答

这样前端可以真正展示“智能体正在做什么”。

## 9. Tool 与 MCP 设计

## 9.1 设计目标

智能体如果只能聊天，能力边界会非常明显。  
因此从整体设计上，应让系统具备“调用外部能力”的统一入口。

## 9.2 本地 Tool 设计

本地工具适合承接以下能力：

- 文档导出
- 文件生成
- 结构化结果落地

典型例子如：

- 根据模型生成的内容导出为 `.docx`

本地 Tool 适合通过统一 Provider 注册，让智能体只关心“工具名 + 参数”，而不直接依赖具体实现类。

## 9.3 MCP 工具设计

MCP 更适合承接以下能力：

- 地图服务
- 联网搜索
- 外部实时工具
- 后续更多第三方工具能力

设计上应支持：

- 一个服务接入多个 MCP Client
- 本地 Tool 与 MCP Tool 统一暴露给 Agent
- 工具接入方式可插拔，而不是写死在主流程中

---

## 10. 前端工作台设计

## 10.1 设计目标

前端需要体现的是“智能体工作过程”，而不是“只显示一句最终答案”。

因此前端工作台应支持：

- 会话管理
- 历史消息恢复
- 流式回答展示
- ReAct 中间事件展示
- 用户主动中断生成

## 10.2 交互方式设计

前后端通信建议以 SSE 为主，原因如下：

- 相比轮询更实时
- 相比 WebSocket 实现更轻量
- 适合模型逐段输出和过程事件输出

SSE 事件建议包括：

- `answer_delta`
- `final_answer`
- `step_planned`
- `tool_started`
- `tool_finished`
- `step_failed`
- `done`

## 10.3 状态管理设计

前端应有统一状态管理层负责：

- 当前会话状态
- 消息列表状态
- 流式连接状态
- 错误状态
- 中间过程事件状态

这样可以保证后续页面和组件继续扩展时仍然清晰可控。

---

## 11. 数据存储与中间件设计

## 11.1 MySQL

MySQL 负责存储：

- 会话元数据
- 对话历史
- 摘要状态

它承担的是“业务持久化主库”职责。

## 11.2 Redis

Redis 负责存储：

- 最近窗口对话
- 摘要缓存
- 高频会话上下文

它承担的是“低延迟上下文缓存层”职责。

## 11.3 RocketMQ

RocketMQ 负责：

- 摘要生成异步解耦
- 后续任务型操作的异步扩展

它承担的是“智能体后处理任务总线”职责。

## 11.4 PostgreSQL + pgvector

PostgreSQL 承担知识库存储与检索职责，负责：

- 文档分块存储
- 全文检索
- 向量检索
- 入库任务记录

它承担的是“知识增强专用数据底座”职责。

---

## 12. 预期落地效果

按照这套架构设计落地后，系统应具备以下能力特征：

- 可以稳定管理多会话和历史消息
- 可以在长对话中维持记忆，而不是越聊越乱
- 可以基于知识库做增强回答，而不是只依赖大模型裸答
- 可以处理需要多步执行的复杂任务
- 可以接入地图、搜索、文档导出等外部能力
- 可以把智能体的中间过程透明展示给用户

这意味着项目最终形态不再是“聊天机器人”，而是一个具备记忆、检索、工具和任务执行能力的智能体系统。

---

## 13. 后续演进方向

在当前整体架构之上，后续可继续演进以下方向：

- 在主脑服务中增加更明确的意图识别与服务路由能力
- 增加统一鉴权、权限与审计能力
- 增加知识库自动化导入流水线
- 增加更多本地 Tool 与 MCP 工具
- 增加监控、链路追踪和指标体系
- 增加多模型调度与成本治理能力

这些演进不会推翻当前架构，而是在当前分层设计上自然扩展。

## 14. 总结

本项目整体架构从设计上就不是围绕“单接口调用大模型”展开，而是围绕“一个可持续扩展的智能体平台”展开。

核心设计判断如下：

- 用 `ai-kitchen-brain-service` 承载主脑能力
- 用 `ai-utility-agent-service` 承接通用能力扩展
- 用 Redis + MySQL + RocketMQ 构建可治理的记忆体系
- 用 PostgreSQL + pgvector 构建独立 RAG 体系
- 用 ReAct 构建复杂任务执行能力
- 用 Tool / MCP 构建外部行动能力
- 用 Vue3 + SSE 构建可观测的智能体工作台

这套设计既能支撑当前实现，也能解释后续为什么具体技术实现会自然落到现在的模块与能力结构上。
